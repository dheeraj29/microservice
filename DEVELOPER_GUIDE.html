1. Executive Summary & Design Principles

OmniBus is an enterprise-grade, cloud-native intercity bus reservation and fleet management system built with Java 21 LTS, Spring Boot 3.2.x / 4.x, Spring Cloud Gateway, Keycloak 26+ IAM, Valkey 8+, and Angular 22.

Zero-Trust Edge Security

No JWT access or refresh tokens are ever exposed to client-side JavaScript. All sessions use opaque HttpOnly cookies managed by a dedicated BFF Gateway.

Distributed Concurrency Safety

Valkey SET NX PX 5000 distributed mutex prevents duplicate Keycloak token refresh race conditions from parallel AJAX requests.

Zero External Dependencies

Runs fully locally out of the box with embedded Apache Maven 3.9.9, Standalone Keycloak 26.0.7, in-memory H2 databases, and host-bridged containers.

3. Back-Channel Token Security (The Token Handler Pattern)

🛡️

Why the Browser NEVER Sees the Access Token

In classical SPA setups, calling /protocol/openid-connect/token in JavaScript exposes the raw JWT access token to DOM memory, localStorage, or sessionStorage. An attacker injecting malicious JavaScript (XSS) or compromising an npm package can exfiltrate the JWT with a single line of code. In OmniBus, the browser never makes or receives a /token request.

Back-Channel Token Exchange Sequence

All token handling occurs server-to-server over encrypted back-channel connections:

Step 1: User Initiates Login
Browser (Angular) triggers GET /auth/login. The Gateway redirects the browser to the Keycloak Authorization endpoint: 
/protocol/openid-connect/auth?client_id=angular-client&response_type=code&redirect_uri=http://localhost:4200/callback&prompt=login
Step 2: User Authenticates in Keycloak
The user enters credentials on the Keycloak login screen. Keycloak validates the user and issues an HTTP 302 Redirect containing a 60-second single-use authorization code: 
http://localhost:4200/callback?code=AUTH_CODE_123
Step 3: Zero Token Exposure in Browser (BFF Handoff)
The Angular CallbackComponent extracts the code and immediately invokes the Gateway BFF endpoint: 
GET /auth/callback?code=AUTH_CODE_123
Crucial Security: The browser JavaScript NEVER makes a direct /token request and NEVER receives raw JWTs!
Step 4: Server-to-Server Back-Channel Token Exchange
The Gateway BFF makes an internal back-channel POST /protocol/openid-connect/token call directly to Keycloak to exchange the authorization code for raw tokens: 
Keycloak Returns: { "access_token": "eyJ...", "refresh_token": "eyJ..." } (Server-to-Server Only)
Step 5: Opaque Session & Cookie Establishment
The BFF generates a random UUID session ID (e.g. sid_7a9f8b2c...), stores the raw JWTs in Valkey (TTL 30 min), and responds to the browser with: 
Header: Set-Cookie: __Host-OmniSession=sid_7a9f8b2c...; HttpOnly; Secure; SameSite=Lax; Path=/
JSON:   { "authenticated": true, "username": "admin", "roles": ["ADMIN"] }   <-- ZERO JWT!
Step 6: Client-Side Angular Signals Transition
The Angular CallbackComponent receives the sanitized user payload, updates the reactive currentUser Signal, and calls router.navigate(['/admin']) for an instant client-side transition with zero full-page reload.

Classical Insecure SPA (What We Avoided)

  • Tokens stored in localStorage / memory
  • Vulnerable to Cross-Site Scripting (XSS)
  • Browser extensions can steal raw bearer tokens
  • No central revocation mechanism

OmniBus Token Handler Pattern (BFF)

  • Tokens stored purely in Valkey server-side
  • 100% immune to XSS token theft via HttpOnly
  • Downstream microservices receive standard Bearer JWTs
  • Central instant session revocation kill switch

Cloud WAF & Edge Threat Intelligence (Why Cookies Outperform Client Bearer Headers)

A critical architectural reason major cloud providers (AWS WAF, Cloudflare Bot Management, Google Cloud Armor, Akamai Edge) mandate cookie-based authentication over client-managed Bearer headers is Edge Threat Intelligence & Anomaly Detection:

1. Anomaly & Session Hijack Detection at the Edge

Cloud WAFs bind session cookies to edge TLS client fingerprints (JA4 / JA3), IP velocity metrics, and device telemetry. If an attacker intercepts or steals a session cookie and attempts to replay it from a different IP, cloud data center, or headless bot client (e.g. curl, Python requests), the Cloud WAF detects the TLS/IP fingerprint mismatch and instantly terminates the request at the edge before it ever reaches backend compute!

2. Browser-Enforced Sandbox Isolation

While an arbitrary script or malware can easily forge custom Authorization: Bearer headers, it cannot manipulate or forge native HttpOnly; Secure; SameSite=Lax browser cookies across origins. The browser engine itself acts as a cryptographic sandbox enforcing origin boundaries.

4. OAuth 2.0 & OIDC Standards & RFC Specifications

RFC / Specification Standard Requirement How OmniBus Implements It
OAuth 2.0 Security BCP
(RFC 6749 / RFC 8252 / RFC 9700)		 Deprecate Implicit Grant. Enforce Authorization Code flow with Token Handler pattern. Browser only handles single-use code. Server-side Gateway exchanges code for tokens and manages token lifecycle.
Cookie Security Spec
(RFC 6265bis)		 __Host- cookie prefix prevents sub-domain cookie tossing and requires Secure; Path=/. Cookies issued with __Host-OmniSession, HttpOnly=true, Path=/, and SameSite=Lax.
Refresh Token Rotation
(RFC 6749 Section 6 / RFC 6819)		 Single-use refresh tokens with immediate invalidation on rotation. Valkey distributed mutex locks refresh calls; rotates Session ID on every refresh with 10s grace alias.
RP-Initiated Logout 1.0
(OpenID Connect Spec)		 Relying Party must terminate identity provider SSO session on logout. /auth/logout redirects to Keycloak's /protocol/openid-connect/logout with post_logout_redirect_uri.
Forced Re-authentication
(OIDC Core 1.0 Section 3.1.2.1)		 prompt=login forces identity provider to prompt for credentials regardless of active SSO cookie. /auth/login includes prompt=login, allowing seamless switching between admin and john_doe.

Multi-Domain & Subdomain Architecture Strategy (When __Host- Needs Adaptation)

🌐

The RFC 6265bis Constraint on __Host-

By strict specification, cookies using the __Host- prefix MUST NOT contain a Domain attribute and MUST have Path=/. This means a cookie named __Host-OmniSession set by app.example.com will never be sent to sibling subdomains like admin.example.com or api.example.com.

If your enterprise topology requires multi-subdomain or multi-domain sharing, follow these standardized architectural patterns:

Topology Requirement Recommended Cookie / Auth Strategy Configuration Details & Tradeoffs
Single Origin
(e.g. app.example.com only)		 __Host- Prefix
(Our Current Setup)		 Set-Cookie: __Host-OmniSession=sid_123; Path=/; Secure; HttpOnly; SameSite=Lax
Highest security level; completely immune to subdomain cookie tossing.
Multi-Subdomain Sharing
(e.g. app.example.com + admin.example.com + api.example.com)		 __Secure- Prefix with Domain Scope Set-Cookie: __Secure-OmniSession=sid_123; Domain=.example.com; Path=/; Secure; HttpOnly; SameSite=Lax
The __Secure- prefix enforces HTTPS transmission, while Domain=.example.com allows all sibling subdomains under the apex domain to share the active authenticated session.
Disjoint Apex Domains
(e.g. booking.com and fleetops.io)		 Federated Central OIDC SSO
(Cloud Enterprise Standard)		 Each apex domain runs its own Gateway/BFF with independent first-party __Host- cookies. Both BFFs authenticate against the central Keycloak 26+ IAM cluster via standard OIDC SSO redirects. Retains 100% __Host- security on each domain with zero reliance on deprecated 3rd-party cookies!

5. Valkey Distributed Concurrency Locking

The Concurrency Race in Modern Single Page Applications

When an access token expires, a dashboard page might fire 4 simultaneous AJAX requests (User Profile, Fleet Stats, Live Routes, Notifications). If each request independently attempts to refresh the single-use Keycloak refresh token:

  • Request 1 succeeds and rotates the refresh token in Keycloak.
  • Requests 2, 3, and 4 present the now-invalidated old refresh token.
  • Keycloak flags a Refresh Token Replay Attack and forcefully terminates the user's entire session!

Our Solution: Valkey Distributed Mutex

In DistributedSessionManager.java, token refresh is coordinated using an atomic Valkey distributed lock: 

public Mono<SessionRecord> refreshAndRotateSession(SessionRecord currentSession) {
    String lockKey = "lock:refresh:" + currentSession.getSessionId();
    String lockVal = UUID.randomUUID().toString();

    // Atomic SET NX PX 5000 (Acquire lock with 5-second auto-expiry)
    return redisTemplate.opsForValue().setIfAbsent(lockKey, lockVal, Duration.ofSeconds(5))
        .flatMap(acquired -> {
            if (Boolean.TRUE.equals(acquired)) {
                // Winner Thread: Execute Keycloak OIDC refresh & rotate Session ID
                return executeRefreshAndRotation(currentSession, lockKey);
            } else {
                // Parallel Threads: Sleep 80ms and consume newly refreshed token via pointer
                return Mono.delay(Duration.ofMillis(80))
                    .flatMap(d -> resolveSession(currentSession.getSessionId()));
            }
        });
}

6. Atomic Session ID Rotation & The 10-Second Grace Pointer

Why Rotate Session IDs?

If an attacker ever managed to intercept a session ID on an insecure network, rotating the ID on every token refresh renders the stolen ID permanently dead within seconds.

The 10-Second Bridge Pointer

If parallel AJAX requests were already in-flight over fiber optic cables when rotation happened, the 10-second alias pointer:old_sid -> new_sid ensures they succeed without dropping.

Step 1: Session Refresh Triggered
Gateway detects access token has < 45s remaining. Acquires Valkey lock.
Step 2: Keycloak Token Handover
Gateway refreshes tokens with Keycloak and generates brand-new SID_200.
Step 3: Valkey Atomic Pipeline
Saves session:SID_200 (30 min TTL) • Sets pointer:SID_100 -> SID_200 (10s TTL) • Adds revoked_archive:SID_100 (1hr TTL) • Deletes session:SID_100.
Step 4: Cookie Rotation to Browser
HTTP response returns Set-Cookie: __Host-OmniSession=SID_200. Browser automatically updates cookie.

7. Breach Detection & Emergency Revocation Kill Switch

If an expired old_sid is presented to the Gateway after the 10-second grace pointer has expired, the system recognizes a Session Hijacking / Replay Attempt.

🚨

Automated Intrusion Response Protocol

1. Flags security alert: STOLEN SESSION REPLAY DETECTED.
2. Calls Keycloak POST /protocol/openid-connect/revoke to kill all tokens cluster-wide.
3. Purges active sessions from Valkey.
4. Clears browser cookies and sends HTTP 401 Unauthorized.

15. Decentralized Embedded BFF Architecture (Pattern 3)

🏛️

Separation of Pure L7 Routing from Microservice Session Resolution

In Pattern 3, the API Gateway is stripped of all business and session logic, operating as a 100% pure, stateless Layer-7 reverse proxy. The BFF security layer is packaged into the reusable common-security library (com.da.demo:common-security:1.0.0) and injected directly into each microservice.

Step 1: Browser Fires Request
Browser sends AJAX request carrying the HttpOnly session cookie: 
Cookie: __Host-OmniSession=sid_abc123...
Step 2: Stateless Gateway L7 Forwarding
The API Gateway (acting purely as a reverse proxy) forwards the request and cookie untouched to the target microservice (e.g. lb://adminservice:8081).
Step 3: Embedded Ingress Security Filter (common-security)
The microservice's BffSessionAuthenticationFilter intercepts the request:
  • Extracts session ID from cookie: sid_abc123...
  • Retrieves SessionRecord from the shared Valkey cluster in $O(1)$ time.
  • If token lifetime has < 45s remaining, acquires Valkey SET NX PX 5000 distributed lock and rotates session.
  • Directly reads cached session.getUsername() and session.getRoles() with zero JWT cryptographic parsing overhead!
  • Populates Spring's SecurityContextHolder with authenticated principal and roles.
Step 4: Domain Business Logic Execution
The downstream Spring MVC Controller executes business logic and database persistence, returning a secure JSON response.

⚡ High-Performance Valkey User Info & Role Caching

A key performance optimization in OmniBus is that cryptographic JWT decoding is NOT performed on every incoming request:

Login & Refresh Time (Parsed ONCE)

When Keycloak issues tokens during initial login or token rotation, the Nimbus JOSE parser extracts the preferred_username and realm_access.roles claims once. The parsed user details are stored directly inside the JSON-serialized SessionRecord in Valkey.

Regular Request Time (Zero-Parsing O(1) Lookup)

On every subsequent request, BffSessionAuthenticationFilter performs a single Valkey Redis GET session:sid, reads session.getUsername() and session.getRoles() directly from memory, and populates the SecurityContext. This eliminates cryptographic verification overhead on high-throughput microservices.

D. Dual-Mode Feign Request Interceptor (FeignAuthRequestInterceptor.java)

The interceptor dynamically checks the current execution thread. If a user is active in RequestContextHolder, it forwards the user's cookie (Token Relay). If running in a background cron/async thread, it fetches a dedicated M2M token from Keycloak: 

package com.da.demo.security.feign;

@Component
public class FeignAuthRequestInterceptor implements RequestInterceptor {

    private final M2MTokenService m2mTokenService;

    public FeignAuthRequestInterceptor(M2MTokenService m2mTokenService) {
        this.m2mTokenService = m2mTokenService;
    }

    @Override
    public void apply(RequestTemplate template) {
        ServletRequestAttributes attributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();

        if (attributes != null && attributes.getRequest() != null) {
            // MODE A: In-Flight User Request -> Token Relay (Relays Cookie & Auth Header)
            HttpServletRequest request = attributes.getRequest();
            if (request.getCookies() != null) {
                for (Cookie cookie : request.getCookies()) {
                    if ("__Host-OmniSession".equals(cookie.getName()) || "OmniSession".equals(cookie.getName())) {
                        template.header("Cookie", cookie.getName() + "=" + cookie.getValue());
                    }
                }
            }
        } else {
            // MODE B: Background @Scheduled Task / Async Thread -> M2M Service Account
            String m2mToken = m2mTokenService.getInternalM2MToken();
            template.header("Authorization", "Bearer " + m2mToken);
            template.header("X-Authenticated-User", "system_scheduler");
        }
    }
}

G. Valkey Caching in M2MTokenService.java (Prevents Keycloak Throttling)

When a background Feign call triggers, M2MTokenService checks Valkey cache key m2m:token:internal-backend-client. If present, it reuses the cached token in $O(1)$ time. 17. Security Architecture & Threat Defense Deep Q&A

Q1: Can someone create tokens from the outside using Postman if they know the Keycloak URL and credentials?

Answer: NO. Every outside attack vector is locked down:

  • Public Client (angular-client): We set directAccessGrantsEnabled: false. Postman cannot send username/password to get tokens. Keycloak rejects it with grant_type not allowed.
  • Through API Gateway: The Gateway (port 8080) only exposes /auth/login (redirect) and /auth/callback (code exchange). It never routes direct /token requests from the outside.
  • Internal Service Client (internal-backend-client): Has standardFlowEnabled: false (cannot be used in a browser) and is accessible only on the private internal network (Kubernetes ClusterIP / localhost), with zero WAN routing.

Q2: If Keycloak is internal, how does the browser load the login page?

Answer: Through OIDC Front-Channel vs. Back-Channel separation:

  • Front-Channel (Browser UI): The browser only visits the interactive login page (/protocol/openid-connect/auth) to display the HTML form and return a 60-second one-time Authorization Code (?code=xyz).
  • Back-Channel (Machine-to-Machine): Microservices and the BFF Gateway exchange authorization codes and fetch M2M tokens directly over the private internal network (/protocol/openid-connect/token). The browser never hits this endpoint.

Q3: Does the browser know the Realm name? Is that a risk, and can it be hidden?

Answer: Knowing the realm name is standard and completely safe, but it can also be 100% hidden:

  • In OAuth 2.0 (Google, Microsoft, Okta, Keycloak), the Realm/Tenant name is public metadata (like a domain name). It grants zero permissions without valid credentials and PKCE code verifiers.
  • If you want it 100% hidden: You can use Gateway URL Vanity Masking (e.g. app.com/login internally proxied) or render an In-App Embedded Login Form directly inside Angular that POSTs to the BFF Gateway.

Q4: How do @Scheduled crons and background workers authenticate without a user?

Answer: Via the Smart Feign Request Interceptor (Dual-Mode):

  • User-Initiated Calls: FeignAuthRequestInterceptor relays the active user's session cookie / JWT from RequestContextHolder (Token Relay).
  • Background / @Scheduled Tasks: When no HTTP request exists in the thread, the interceptor falls back to M2MTokenService to acquire an internal M2M token using internal-backend-client (Service Account), caches it in Valkey for 5 minutes, and injects Authorization: Bearer <m2m_jwt>.

Q5: Why is JWT parsing skipped on every regular request?

Answer: High-Performance Valkey User Info & Role Caching: The JWT is parsed ONCE during initial login code exchange or token refresh via Nimbus JOSE. The extracted username and roles are stored directly inside the JSON SessionRecord in Valkey. Subsequent API requests perform a single O(1) Redis lookup and directly read session.getUsername() and session.getRoles() with zero cryptographic parsing overhead per request.

Q6: Why Client Credentials for internal calls? What are the modern alternatives?

Answer: RFC 6749 Client Credentials is the industry standard for M2M communication. For ultra-high security zero-trust clusters, modern alternatives include:

  • Private Key JWT (RFC 7523): Uses asymmetric public/private keys instead of shared client secrets.
  • SPIFFE / SPIRE & Istio mTLS: Cryptographic x509 SVID client certificates automatically rotated by the service mesh control plane.
  • Kubernetes Projected ServiceAccount Tokens: Short-lived OIDC tokens bound to the Kubernetes Pod identity.

Q7: Why choose Pattern 3 (Decentralized Embedded BFF) over Pattern 1 (Centralized Gateway BFF)?

Answer: Zero Gateway Bottleneck & Direct Kubernetes Migration: In Pattern 1, the API Gateway is stateful, CPU-bound by token resolution, and difficult to scale. In Pattern 3, the Gateway is a 100% stateless pure L7 router (which can be replaced by Envoy Gateway / Istio without code changes), while session resolution is distributed across all microservices using shared Valkey caching.

Q8: How do we prevent token refresh race conditions when 10 AJAX requests arrive simultaneously?

Answer: Valkey Distributed Mutex + 10-Second Grace Pointer: The first thread to detect token expiration acquires a Valkey distributed lock (SET NX PX 5000) and rotates the session in Keycloak. The other 9 threads wait 80ms, detect the update, and follow the temporary grace pointer (pointer:<old_sid> -> <new_sid>) with 10s TTL, ensuring 100% of concurrent requests succeed with zero dropped calls.

Q9: How do all 4 interceptors work together without conflicts?

Answer: Multi-Tier Layer Separation: login.interceptor.ts operates in the browser client; csrfHeaderFilter operates at the Edge Gateway; BffSessionAuthenticationFilter operates at the microservice HTTP ingress; and FeignAuthRequestInterceptor operates at the cross-service Feign egress. Each performs a discrete role in the end-to-end security chain.

Q10: External B2B API Integration: What is the auth standard, and how do we prevent secret leaks?

Answer: The M2M Authentication Spectrum:

⚡ Best Simple & Universal Standard: OAuth 2.0 Client Credentials (RFC 6749)
Supported by 100% of programming languages, SDKs, and platforms globally. The partner's backend calls the token endpoint to receive a short-lived Bearer JWT.
🏆 Best No-Leak Zero-Trust Standard: SPIFFE / SPIRE & Service Mesh mTLS
Zero static secrets, passwords, or keys exist anywhere. Workload identity is cryptographically tied to Linux kernel cgroups / Kubernetes Pod UIDs, and x509 certificates rotate automatically every hour.
🛡️ 4-Layer Defense Against Secret Leaks (B2B Partner Integrations)
  • 1. Private Key JWT (RFC 7523): Partner signs tokens using asymmetric private keys (RSA/EC) locked in their HSM/KMS. No secret is shared or transmitted.
  • 2. mTLS Certificate Binding (RFC 8705): Tokens are bound to the client's TLS cert fingerprint (cnf.x5t#S256) — stolen tokens cannot be replayed.
  • 3. IP CIDR Whitelisting: Keycloak rejects any token requests originating outside the partner's registered egress IP subnets.
  • 4. Least Privilege Scopes: Partners only receive restricted roles (ROLE_PARTNER_READ) with zero access to admin APIs or user databases.

Q12: When a session expires, is the Valkey cache automatically purged? How is zero memory leak guaranteed?

Answer: 4-Tier Native Valkey Auto-Eviction Architecture:

⏳ 1. Native Valkey TTL Engine (30-Minute Expiration)
Every session record is written with a hardware-level TTL: redisTemplate.opsForValue().set("session:" + sid, json, Duration.ofMinutes(30)). Valkey combines passive eviction (instant purge on access when expired) and an active background eviction cycle (sampling 10 times per second), ensuring expired sessions are deleted directly from RAM with zero memory leaks.
🔄 2. Sliding-Window Touch Extension
Every authenticated API call invokes redisTemplate.expire("session:" + sid, SESSION_TTL). Active users never get logged out mid-work, while abandoned/idle sessions expire and are purged precisely 30 minutes after last activity.
⚡ 3. Instant Token Rotation Deletion & 10s Pointers
When an access token rotates, the old session is immediately deleted via redisTemplate.delete("session:" + oldSid). The in-flight forwarding pointer (pointer:<oldSid> -> <newSid>) is given an ultra-short 10-second TTL (POINTER_TTL) and auto-evicts seconds later.
🚪 4. Explicit Logout Teardown (/auth/logout)
When a user clicks Logout, destroySession() executes immediate Valkey key deletion (redisTemplate.delete("session:" + sid)) and triggers an OIDC back-channel revocation request to Keycloak to invalidate the refresh token.
